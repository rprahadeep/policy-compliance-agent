AI-POWERED POLICY COMPLIANCE INTELLIGENCE ASSISTANT
PROJECT ARCHITECTURE, TECH STACK, AND END-TO-END WORKFLOW

1. PROJECT OVERVIEW

This project is an AI-powered policy compliance assistant for answering employee compliance questions using official policy PDF documents.

The system lets a user ask natural-language questions such as:

- Do privileged user accounts need multi-factor authentication?
- If I accidentally view customer data unrelated to my project, should I report it?
- What checks are required before buying a new SaaS vendor tool?
- When does a system need security assessment and authorization?

The assistant retrieves relevant policy sections from the local PDF documents, reasons over the retrieved policy context using a LangGraph multi-agent workflow, and returns:

- A clear compliance answer
- Compliance status
- Risk level and risk score
- Risk rationale
- Recommended next steps
- Source citations from policy PDFs
- Agent trace showing what each agent did
- Analytics for dashboard usage

The system is designed as a full-stack project:

- Backend: FastAPI microservice
- Agent orchestration: LangGraph
- LLM: OpenAI GPT-4o-mini
- Embeddings: OpenAI text-embedding-3-small
- Vector database: Pinecone
- Frontend: React with Vite
- Documents: 4 NIST-style policy PDF files located in backend/data/policies

6. BACKEND API ENDPOINTS

Base URL:

http://localhost:8000

Endpoints:

GET /health
  Purpose:
  Checks whether the backend is running.

  Example response:
  {
    "status": "ok",
    "model": "gpt-4o-mini",
    "index": "policy-compliance-agent"
  }

GET /api/v1/policies
  Purpose:
  Lists the local policy PDFs found in backend/data/policies.

  Returns:
  - policy name
  - relative path
  - page count
  - file size
  - category
  - framework

POST /api/v1/ingest
  Purpose:
  Reads the local PDF files, chunks them, embeds each chunk, upserts vectors to Pinecone, and saves chunk metadata locally.

  This endpoint must be called before asking policy questions.

  Internal steps:
  1. Validate OpenAI and Pinecone environment variables.
  2. Read all PDF files from backend/data/policies.
  3. Extract text from each PDF page.
  4. Normalize extracted text.
  5. Infer policy category from the filename.
  6. Split policy text into overlapping chunks.
  7. Generate OpenAI embeddings for each chunk.
  8. Create Pinecone index if it does not already exist.
  9. Upsert embedded chunks to Pinecone with metadata.
  10. Save chunk metadata to backend/storage/chunks.jsonl.

  Example response:
  {
    "indexed_chunks": 42,
    "policies": ["Information Security Policy", "..."],
    "index_name": "policy-compliance-agent",
    "local_store_path": "storage/chunks.jsonl"
  }

POST /api/v1/query
  Purpose:
  Accepts a user compliance question, retrieves relevant policy sections, runs the LangGraph agent workflow, and returns a grounded compliance answer.

  Request body:
  {
    "question": "Do privileged user accounts need multi-factor authentication before accessing company systems?",
    "employee_context": "Employee is requesting elevated access to an internal production administration console.",
    "filters": {
      "category": "Identification and Authentication",
      "framework": null,
      "policy_name": null
    },
    "top_k": 8
  }

  Response includes:
  - answer
  - compliance_status
  - risk
  - recommendations
  - citations
  - agent_trace
  - token_usage

GET /api/v1/analytics
  Purpose:
  Returns dashboard analytics based on previous user queries.

  Includes:
  - total query count
  - compliance status counts
  - risk level counts
  - common topics
  - recent queries

POST /api/v1/evaluate/retrieval
  Purpose:
  Lightweight retrieval evaluation endpoint.

  Accepts test cases with expected terms and calculates context precision based on whether expected terms appear in retrieved chunks.


7. PDF INGESTION WORKFLOW

The ingestion pipeline is implemented mainly in:

- app/services/documents.py
- app/services/pinecone_store.py
- app/services/local_store.py
- app/main.py

Detailed ingestion flow:

1. User clicks "Sync policy index" in the frontend or calls:
   POST /api/v1/ingest

2. FastAPI enters the ingest endpoint in app/main.py.

3. The backend validates that required environment variables exist:
   - OPENAI_API_KEY
   - PINECONE_API_KEY

4. The backend scans backend/data/policies for PDF files.

5. For each PDF:
   - pypdf opens the file.
   - Text is extracted page by page.
   - Each page gets metadata:
     - policy_name
     - category
     - framework
     - page number
     - text

6. Text normalization removes unwanted characters, repeated whitespace, and excessive blank lines.

7. The chunker splits page text into overlapping chunks.

   Current chunking strategy:
   - Approximate chunk size: 3600 characters
   - Overlap: 450 characters
   - Attempts to split near paragraph or sentence boundaries
   - Preserves policy metadata
   - Detects section headings when possible

8. Each chunk receives a stable ID:
   Example:
   identification-and-authentication-policy-p1-c1

9. OpenAI text-embedding-3-small generates embeddings for each chunk.

10. Pinecone index is created if it does not exist.

    Index settings:
    - Name: policy-compliance-agent
    - Dimension: 1536 for text-embedding-3-small
    - Metric: cosine
    - Serverless cloud and region from .env

11. Each chunk is upserted to Pinecone with:
    - vector values
    - text
    - policy_name
    - category
    - framework
    - page
    - section

12. Chunk records are also saved locally to:
    backend/storage/chunks.jsonl

    This local store supports keyword scoring and citation metadata.


8. QUERY WORKFLOW

The query workflow is implemented mainly in:

- app/main.py
- app/services/guardrails.py
- app/services/retrieval.py
- app/services/pinecone_store.py
- app/services/agents.py
- app/services/analytics.py

Detailed query flow:

1. User enters a question in the React frontend.

2. Optional user inputs:
   - Employee context
   - Policy category filter
   - Scenario template
   - Context chips

3. Frontend sends a POST request to:
   /api/v1/query

4. FastAPI validates the request body using QueryRequest in app/models/schemas.py.

5. Backend validates required environment variables.

6. Backend builds the LangGraph compliance graph.

7. LangGraph starts with the validate_input node.

8. Input guardrails check:
   - question is not empty
   - question is not too long
   - question appears related to policy/compliance/security/data/access
   - question does not try to bypass system instructions

9. If guardrails fail:
   - The graph routes to blocked_response.
   - The API returns a safe response asking the user to rephrase the question.

10. If guardrails pass:
    - The graph routes to retrieve_policy.

11. Hybrid retrieval runs:

    A. Semantic retrieval:
       - The user question is embedded with OpenAI.
       - Pinecone returns the most similar policy chunks.
       - Metadata filters are applied when present.

    B. Keyword retrieval:
       - Local chunks are loaded from storage/chunks.jsonl.
       - Query terms are tokenized.
       - Chunks are scored based on keyword overlap and inverse document frequency.

    C. Reranking:
       - Semantic score and keyword score are combined.
       - Authority weights boost certain policy categories.
       - Top results are returned to the graph.

12. Policy Retrieval Agent output:
    - Stores retrieved chunks in graph state.
    - Adds a trace message showing how many chunks were retrieved.

13. Policy Interpretation Agent:
    - Receives the user question, employee context, and retrieved policy chunks.
    - Uses GPT-4o-mini.
    - Explains what the cited policy context supports.
    - Avoids unsupported external claims.

14. Compliance Checker Agent:
    - Receives the interpreted policy meaning.
    - Uses GPT-4o-mini.
    - Produces strict JSON with:
      - status
      - reasoning

    Valid status values:
    - compliant
    - non_compliant
    - needs_review
    - unclear

15. Risk Assessment Agent:
    - Receives question, status, and compliance reasoning.
    - Uses GPT-4o-mini.
    - Produces strict JSON with:
      - level
      - score
      - reasoning
      - escalate

    Valid risk levels:
    - low
    - medium
    - high
    - critical
    - unknown

16. Recommendation Agent:
    - Receives interpretation, status, and risk.
    - Uses GPT-4o-mini.
    - Produces 3 to 5 recommended actions.

17. Final Response Agent:
    - Receives:
      - original question
      - interpretation
      - compliance status
      - risk assessment
      - recommendations
      - citations
    - Uses GPT-4o-mini.
    - Produces a concise final answer grounded in policy sources.

18. API formats citations:
    Each citation includes:
    - source_id
    - policy_name
    - page
    - section
    - category
    - framework
    - excerpt
    - score

19. Query analytics are recorded:
    - timestamp
    - question
    - status
    - risk level
    - risk score
    - extracted topics

20. Frontend displays:
    - compliance decision
    - risk score
    - source coverage
    - final answer
    - action plan
    - risk rationale
    - evidence citations
    - agent trace
    - dashboard metrics


9. LANGGRAPH MULTI-AGENT ARCHITECTURE

The multi-agent system is implemented in:

backend/app/services/agents.py

The graph state is represented by ComplianceState.

Important state fields:

- question
- employee_context
- filters
- top_k
- valid
- guardrail_message
- retrieved_chunks
- interpretation
- compliance_status
- compliance_reasoning
- risk
- recommendations
- answer
- agent_trace
- token_usage

Graph nodes:

1. validate_input
   Role:
   Input Guardrail Agent

   Responsibilities:
   - Validate the user question
   - Reject prompt injection attempts
   - Reject unrelated questions

2. retrieve_policy
   Role:
   Policy Retrieval Agent

   Responsibilities:
   - Run hybrid retrieval
   - Retrieve relevant policy sections
   - Store retrieved chunks in state

3. interpret_policy
   Role:
   Policy Interpretation Agent

   Responsibilities:
   - Translate policy language into clear explanation
   - Stay grounded in retrieved policy context

4. check_compliance
   Role:
   Compliance Checker Agent

   Responsibilities:
   - Determine if the requested action is compliant
   - Return compliance status and reasoning

5. assess_risk
   Role:
   Risk Assessment Agent

   Responsibilities:
   - Evaluate violation severity
   - Assign risk level
   - Assign risk score
   - Decide whether escalation is recommended

6. recommend_actions
   Role:
   Recommendation Agent

   Responsibilities:
   - Suggest compliant next steps
   - Suggest safer alternatives
   - Suggest escalation paths when needed

7. compose_answer
   Role:
   Final Response Agent

   Responsibilities:
   - Produce the final user-facing answer
   - Ground the answer in policy citations
   - Mention escalation if needed

8. blocked_response
   Role:
   Safe Rejection Node

   Responsibilities:
   - Return safe response when guardrails fail

Graph path for valid questions:

validate_input
  -> retrieve_policy
  -> interpret_policy
  -> check_compliance
  -> assess_risk
  -> recommend_actions
  -> compose_answer
  -> END

Graph path for invalid questions:

validate_input
  -> blocked_response
  -> END


10. HYBRID RETRIEVAL DESIGN

Hybrid retrieval is implemented in:

backend/app/services/retrieval.py

The project does not rely only on vector similarity. It combines semantic search and keyword matching.

Why hybrid retrieval is useful:

- Compliance documents often contain exact terms.
- Important phrases like "multi-factor authentication", "authorization", "incident", or "access" should be matched precisely.
- Semantic search helps when the user asks in natural language.
- Keyword search helps preserve exact policy terminology.

Hybrid retrieval steps:

1. Load local chunks from storage/chunks.jsonl.

2. Apply metadata filters:
   - category
   - framework
   - policy_name

3. Run keyword scoring:
   - tokenize query
   - tokenize chunks
   - compute term frequency and inverse document frequency
   - normalize scores

4. Run Pinecone semantic search:
   - embed query
   - query Pinecone
   - retrieve matching vector records

5. Merge semantic and keyword candidates.

6. Rerank with:
   - 72 percent vector score
   - 28 percent keyword score
   - authority weight by policy category

7. Return top_k chunks.

16. COMPLIANCE STATUS AND RISK MODEL

Compliance status values:

- compliant
  The requested action appears allowed or required under the retrieved policy context.

- non_compliant
  The requested action conflicts with retrieved policy requirements.

- needs_review
  The action may be allowed but requires approval, review, or escalation.

- unclear
  Retrieved evidence is insufficient or ambiguous.

Risk levels:

- low
  Minimal compliance concern.

- medium
  Some compliance risk or missing validation.

- high
  Significant policy violation risk.

- critical
  Severe violation risk or urgent escalation needed.

- unknown
  Risk cannot be confidently determined.

Risk score:

- Integer from 0 to 100.
- Higher score means more severe risk.

Escalation:

- Boolean value.
- true means human review or formal reporting is recommended.

- Supports citation generation

Why both Pinecone and local storage are used:

- Pinecone is best for semantic vector search.
- Local storage is simple and fast for keyword scoring and metadata access.
- Together they enable hybrid retrieval.

Why LangGraph is used:

- The project requirement asks for agents using LangGraph.
- LangGraph makes the reasoning workflow explicit and inspectable.
- Each stage has a clear responsibility.
- Agent trace can be shown in the frontend.

Why GPT-4o-mini is used:

- Lower cost than larger models.
- Fast enough for interactive demo use.
- Strong enough for structured compliance reasoning over retrieved context.

Why Pinecone is used:

- Managed vector database.
- Supports metadata filtering.
- Scales beyond local vector stores.
- Suitable for enterprise RAG systems.

Cause:

Fix:

Add frontend origin to backend/.env:

ALLOWED_ORIGINS=http://localhost:4173,http://127.0.0.1:4173,http://localhost:4174,http://127.0.0.1:4174,http://localhost:5173,http://127.0.0.1:5173

Then restart backend.

Error:

POST /api/v1/query 500 Internal Server Error

Possible causes:

- Missing OPENAI_API_KEY
- Missing PINECONE_API_KEY
- Documents not ingested
- Pinecone index not available
- Invalid Pinecone environment settings

Fix:

1. Check backend terminal traceback.
2. Confirm .env values.
3. Run ingestion again.
4. Restart backend.

Error:

React is not defined

Cause:

JSX runtime expects explicit React imports.

Fix:

React imports were added to JSX components.

Error:

Frontend port already in use

27. FINAL PROJECT DESCRIPTION

The AI-Powered Policy Compliance Intelligence Assistant is a full-stack RAG and multi-agent compliance reasoning system. It ingests NIST-style policy PDF documents, indexes them into Pinecone using OpenAI embeddings, retrieves relevant policy evidence with hybrid search, and uses a LangGraph workflow powered by GPT-4o-mini to interpret policies, assess compliance, score risk, recommend actions, and produce citation-grounded answers through a modern React interface.
